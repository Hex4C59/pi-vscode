## Conclusion

Recommend **one real target, `pi-system-prompt-manager` 0.1.1 at commit `9c8f546b875f929ad5d573fe30e7a7fd6e3ae924`**, for an isolated, unmodified public-RPC test on installed pi **0.86.1**. ## Required interactions from actual handlers

All preferred-target paths below are source inferences from **S2**, not observed runs. All dialogs are awaited, including the nested create helper. No dialog supplies a timeout or AbortSignal.

| Public command / stage | Methods and result handling |
|---|---|
| `/sysprompt` | Awaits `select`; undefined returns immediately. Selecting Add awaits the create flow; selecting a preset persists selection and reports status. |
| `/sysprompt add` | Awaits name `input`; cancel/empty becomes empty and returns. Duplicate name notifies and returns. |
| Create: optional description | Awaits another `input`; **cancel becomes empty description and continues**, rather than cancelling the command. |
| Create: content | Awaits multiline `editor`; cancel/empty notifies and returns without creating the entry. |
| Create: apply mode | Awaits `select`; **cancel defaults to append and still saves/activates** the new prompt. Preserve this upstream behavior; a dismissed dialog is not necessarily a cancelled command. |
| `/sysprompt edit surgical` | Awaits `editor` prefilled with existing text; cancel/empty notifies and returns unchanged. Nonempty input saves. |
| `/sysprompt remove surgical` | Awaits `confirm`; false/cancel returns without deletion. True deletes and, if active, disables selection. |
| `/sysprompt list` / `off` | No dialog; useful public follow-up observations through `notify` and `setStatus`. |

**Bounded-cancellation qualification:** source control flow returns after cancellation of the menu, name, content editor, edit editor, or deletion confirm, with at most local synchronous JSON I/O/feedback on those paths. It contains no continuing loop or long-running external work. Cancelling the optional-description dialog instead reaches another awaited dialog; cancelling the mode dialog commits the default choice and returns. Thus this is not a uniformly cancel-to-stop extension. Filesystem calls have no explicit wall-clock bound, so even the returning paths are source evidence, not a measured latency guarantee. [S2]

An isolated test can use the seeded `surgical` entry and create a uniquely named coding-review prompt. Exercise menu cancellation, cancelled name, cancelled description followed by editor cancellation, editor prefill/edit, cancelled mode selection, and decline/accept deletion. Check subsequent `/sysprompt list` and UI feedback rather than inventing a universal command-completion event. No model-generated assistant content is necessary. This matrix motivates all four standard dialogs; it is not a recovery/queue/budget design.

For the comparator, `/code` awaits `pickSnippet()`, which awaits `custom()` and returns on undefined; public RPC therefore cannot reproduce its normal picker. An explicit numeric index bypasses that picker: `/code 1` then awaits standard action `select`, returning on cancellation. Run next awaits `confirm` and returns on false; accepting executes a shell snippet and presents another custom component. Copy uses external clipboard commands; Insert uses `getEditorText`/`setEditorText`, with degraded editor-read behavior under RPC. No direct model call occurs in the handler, but acquiring assistant history is a separate precondition. Reject as the minimum target; neither shell nor clipboard paths belong in this isolated check. [C2, C3, C5, P1]

## Isolation and public-runtime boundary

**The preferred target hardcodes `join(homedir(), ".pi", "agent")`. `PI_AGENT_DIR` alone is insufficient.** It reads/writes `system-prompts.json` and `system-prompt-state.json`, including default-library seeding at extension load; it does not create the parent directory and silently catches write errors. Root must establish a genuinely isolated effective home and an existing fixture `.pi/agent` directory before loading the unmodified entry. An apparent success notification alone does not prove persistence. Do not point it at the real user home. These files are extension-owned JSON, not pi session files. [S2]

The inspected complete source contains no `exec`, child process, network client, model invocation, `sendUserMessage`, custom TUI, or direct pi session-file access. It has a `before_agent_start` hook that changes a later turn's system prompt; management commands themselves do not initiate that turn. Limit testing to the registered slash commands through public RPC `prompt`; do not submit ordinary model prompts. Absence of network calls in this extension is source evidence, not OS sandbox or runtime-network evidence. [S2]

Local read-only checks found both the repository dependency and installed package at **0.86.1**. Its installed `docs/rpc.md` documents standard dialog request/response support, RPC `hasUI: true`, `custom()` returning undefined, and fire-and-forget feedback. The npm version metadata identifies upstream gitHead `13cbf77df2396303013a41646bcfa77b4271ae56`. [P1, P2]

## Loading and error observability probe

The main agent also ran five owned synthetic entries through the installed 0.86.1 public CLI/RPC in isolated HOME/agent/cwd, with no model prompts or tools. Evidence: dist/delegated-completion-20260928/wi013-load-failures/report.json and asserted-probe.log. The first observation stopped at an expected startup exit; first-observation.json/log preserve that result. The corrected probe distinguishes expected initialization failure from probe failure and asserts every case:

- A factory throwing before registration, or after registering a command, exits with code 1 before any RPC response; stderr contains a loading failure. This does not require parsing error prose to determine that startup failed.
- A session_start hook throwing emits public extension_error but get_state and get_commands still succeed. A command catalogue alone therefore does not establish healthy extension initialization.
- A registered command throwing emits extension_error while the corresponding prompt response still reports success. Prompt success cannot override the error event or prove a successful operation.
- A healthy entry can use documented getAllTools/getCommands at session_start and send a bounded inventory through ordinary UI notify. This is a feasible adapter handshake, not authentication or proof that trusted extension code cannot forge feedback.

All surviving children were closed by the probe owner with observed SIGTERM exits; factory-failure children exited themselves. These observations inform the upcoming readiness/error contract, not product compatibility acceptance. The current production adapter does not yet handle general extension_error, so no claim is made that these failures are already presented correctly in the sidebar. Source for the inventory API is the installed package's public docs/extensions.md section “pi.getActiveTools() / pi.getAllTools() / pi.setActiveTools(names)”; source for the error event is docs/rpc.md “extension_error”.

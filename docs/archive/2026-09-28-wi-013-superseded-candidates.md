## Rationale

The local host owns eligibility and product recovery; the adapter maps validated public evidence and owns transport/process observation; the Webview presents bounded forms and sends named intents; pi owns remote execution and dialog arbitration. This division can prevent stale local actions without falsely reporting remote success. Missing runtime facts are best requested from their upstream owner rather than inferred from notifications or recreated agent internals. Keeping the upstream proposal local permits review without implying upstream agreement.

### Ownership and candidate discriminants

Names below describe a reviewable local schema, not exported TypeScript types or pi wire fields. Before Build, freeze the exact envelopes, errors and version/capability migration with tests; do not silently extend current `version: 2` consumers.

- **Host:** sole owner of admission, operation eligibility, the in-memory interaction ledger, queue, local deadlines, projection and recovery barrier. Each entry binds host epoch, workspace generation, runtime instance/live-session identity, opaque non-reused interaction ID and current view revision. Upstream IDs stay private to the adapter; a UI ID never grants tool permission.
- **Adapter:** owns validated transport correlation, a one-shot reply token per admitted remote request, method-specific mapping and passive owned-child observations. It translates evidence, not product readiness. Host revokes eligibility first; adapter independently consumes a token before any write to guard duplicate calls. Cleanup belongs to the creator of timers/listeners/tokens. Runtime owns remote dialog and execution facts; neither local owner invents them.
- **Operation association:** discriminated `association: { kind: "runtime-scoped", operationId, coverage } | { kind: "reviewed-fixture", evidenceRef } | { kind: "unknown" }`. `runtime-scoped` requires verified public capability bound to the current connection; coverage is `awaited-handler | registered-work | unknown`. A reviewed fixture is limited source-review inference, not general support or an enabled route-2 pilot. Unknown attribution cannot admit operations whose support depends on reliable separation. Host-assigned correlation alone cannot establish provenance. Never infer source from title, notification, `hasUI` or one pending command; runtime attribution is not authentication against co-loaded executable code.
- **Adapter evidence:** separate event discriminants `interaction-opened`, `interaction-closed`, `response-outcome`, `operation-settled`, `transport-lost`, `child-exited`, `spawn-failed`. All bind the relevant runtime/session; operation/dialog events additionally bind their IDs and evidence basis. Close/outcome/settlement variants are emitted only when the selected remote capability supplies that fact. Legacy absence stays unknown, not a synthesized event. `operation-settled` includes `completed | failed | cancelled` and coverage, never blanket cessation of detached work.
- **Host ledger:** independent axes: local validity `queued | active | invalidated`; reply attempt `none | reserved | written-locally | write-failed`; remote dialog `unknown | closed` with evidenced reason/outcome; operation `pending | settled | failed | unknown` with coverage; owned runtime `connected | lost | exited | spawn-failed`. Local invalidation records a bounded reason such as answer-attempt, user-cancel, Stop, local-cutoff, remote-close, replacement or loss. An entry never becomes valid again. A later remote fact may refine evidence, not reopen it.
- **Webview projection:** candidate `interactionState` projects one method-discriminated form (`select` with opaque option IDs/labels, `confirm`, `input`, `editor`), identity/view revision, queue count, `canAnswer`, bounded literal text and evidence-derived status. Candidate `answerInteraction` carries only the identity/view revision plus `answer: { method: "select", optionId } | { method: "confirm", value: boolean } | { method: "input" | "editor", text: string }`; `cancelInteraction` carries identity/view revision only. Stop is a host-coordinated intent, not arbitrary RPC. These named intents are not admitted by today's validator. A negative confirm differs locally from cancellation even if pi maps both to false. Ordinary confirm cannot create or reuse a tool grant.

### Validation, finality and ordering

1. Validate plain objects, exact own fields, supported envelope version/discriminants, bounded identities, current workspace eligibility/runtime/view, active ledger entry and method before mutation. Select must match the original option membership; adapter maps the selected ID to its exact original value. Confirm accepts only boolean; input/editor accept bounded strings without coercion, silent trimming or truncation (empty string stays distinct from cancellation where the method permits it). Reject unknown/extra fields, wrong method, stale or duplicate answers without transport effects; a valid but obsolete UI resynchronizes. Answer payload budgets are checked again immediately before serialization.
2. Serialize terminal arbitration in the host. On answer/cancel, atomically invalidate the entry and reserve its single reply token before awaiting I/O; then attempt the method-specific response once if transport and scope remain eligible. A Stop/replacement/loss that wins before the write suppresses an unsent affirmative response. No retry after uncertain writes and no second cancellation response after an answer attempt. Duplicate intents cause zero additional writes. The guarantee is **exactly one local reservation and at most one write attempt**, not exactly-once remote delivery or execution; some invalidations produce no write at all.
3. On Stop, first block new tasks/admission and invalidate all active/queued answers plus covered pending approvals, then cancel still-unanswered dialogs through supported responses and request queue clearing/operation or agent cancellation as supported. An already-written answer may win remotely; Stop cannot retract it. Ordinary dialog cancellation can resume extension code. Keep stopping until relevant evidenced settlement or explicit unconfirmed failure; neither local write/drain, cancel/abort ACK, `agent_settled`, `promptInFlight=false` nor handler return alone proves arbitrary extension completion. Do not apply pending settings or switch profiles/sessions while unresolved.
4. Remote close invalidates the matching active or queued entry immediately upon observation; delayed close/outcome cannot mutate another scope. Identical duplicate facts are harmless; conflicting finality or missing required ordering fails the affected scope closed with a bounded diagnostic, not guessed success. Registered dialogs/children must be accounted for before a scoped operation can be treated as settled. Ordering depends on the negotiated evidence, not on inventing a global sequence for legacy RPC.
5. View replacement advances view revision and rejects old-page intents; it resynchronizes the same host ledger without restarting deadlines or replaying requests. Workspace/runtime/session replacement and provider disposal invalidate entries before detaching listeners/timers. Retain only the bounded evidence needed for stale rejection/diagnostics; old callbacks cannot update new identity. Draft retention and no automatic replay remain required. Existing WI-010 fault shutdown is unchanged; it is not authority to add automatic kill/restart for WI-013 incompatibility.

Candidate host error codes distinguish `invalid-message`, `invalid-answer`, `unsupported-method`, `source-unknown`, `unsupported-capability`, `overload`, `write-failed`, `transport-lost` and `stop-unconfirmed`. They describe the failing boundary, not upstream exceptions. Invalid input has no action; unsupported admission offers a limitation/terminal route; overload follows the queue policy below; write/loss uncertainty never triggers response retry; unconfirmed Stop holds the recovery barrier. Exact UI wording and error envelopes remain to be frozen before Build.

### Queue, timing and memory bounds

Present one active form and a bounded FIFO queue with visible count. Expire/close queued entries without presenting them; recheck validity/deadline at dequeue and reply. Keep admitted requests on overflow, reject/cancel extras only via supported responses and warn. Sustained overflow enters interaction failure, disables answers and blocks new tasks without claiming execution stopped or automatically restarting. If rejection cannot be sent, remote state stays unknown.

No upstream deadline means no blanket human countdown; hidden private signals may still exist. A declared duration starts upstream before output, not at sidebar display. Receipt plus duration is not the remote deadline or a proven remaining response window. A receipt-based local cutoff would be a separately approved, labeled presentation policy, never an extension of remote validity or a substitute for evidenced expiry. Never restart timing on dequeue or view recreation. Remote deadline metadata must define clock/elapsed-time semantics; late delivery is disclosed. Transport and Stop-settlement deadlines are separate from human response time; the current prompt-response timeout needs redesign before indefinite command dialogs.

**Historical unapproved sizing candidates (the current selected subset is recorded in ADR 0002; this paragraph is not a Build contract):** one active plus seven queued; 64 KiB UTF-8 complete frame (including partial-frame buffer bound), 32 KiB text/answer, 64 options each up to 1 KiB within the aggregate frame; five overflows in ten seconds as a sustained-overflow candidate. Lower peer bounds win. These numbers are not implementation defaults or accepted product limits; usability/transport evidence and approval remain required. Oversized inputs fail explicitly, never silently truncate an answer. Diagnostics exclude content/secrets and use bounded codes/counters with rate limiting.

**Replay bookkeeping is not a lifetime interaction quota.** The earlier 256-terminal-record suggestion does not authorize stopping a healthy connection after 256 dialogs. Candidate local strategy: fresh host/runtime epochs plus monotonic non-reused local IDs, a bounded live-token map and a bounded recent terminal diagnostic ring; an answer requires a live token, so evicting diagnostic text never restores answer eligibility. Counter exhaustion must not wrap/reuse IDs. Remote open-ID replay requires a separately proven non-reuse/sequence-watermark or tombstone policy at the adapter boundary; legacy arbitrary IDs do not supply it. Exact retention, remote duplicate handling and exhaustion policy remain pre-Build gaps, not an adopted consequential policy or unbounded tombstone set.

### Loss, exit and deliberate recovery

`transport-lost` means local answering is disabled and remote execution is unknown. A passive `child-exited` must identify the exact successfully spawned child and observed exit/close details; spawn failure or stream error is not exit evidence. Adapter must retain enough process-observation ownership after stream failure to observe a later real exit. This is a planned capability absent from today's merged loss event. Exit proves only that owned child ended, not descendants, side-effect rollback or operation success.

For already-pending unconfirmed Stop, host owns the recovery barrier: show “stop not confirmed / cannot continue”, preserve draft, block tasks/settings/profile/session transitions, and provide manual runtime-termination guidance. Actual owned-child exit and deliberate user recovery are separate conditions; a recovery click alone is not evidence. After sufficient boundary evidence and explicit recovery, any replacement would use fresh identities, controlled defaults and cleared grants without replay. Host reload loses ledger/child ownership; a new ready process, a PID absence check or user assertion cannot clear old-work uncertainty. How to preserve/enforce this barrier across ownership loss without new persistence or automatic termination is unresolved and **blocks that recovery branch and any selected slice relying on it**, not a claim that memory-only state already enforces it.

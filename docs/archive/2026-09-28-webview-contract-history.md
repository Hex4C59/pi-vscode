## Envelope and allowlist

**Current version and historical shapes:** the v1 forms below and T014-stage v2 fields retain the migration history. Current source accepts only v3; the selected WI-013 v3 section owns exact viewId/generation envelopes. T014 sections continue to own action payloads and transaction semantics, not acceptance of old envelopes. The separate approval-gate envelope remains v1.

Plain objects only, numeric `version: 1`, exactly the listed own fields. The host validates `unknown` before acting. Unknown types/versions, extra fields, malformed values and stale generations cannot execute actions.

- Webview → host `ping`: `{ version: 1, type: "ping" }`; replies with `{ version: 1, type: "pong" }`.
- Webview → host `getWorkspaceState`: `{ version: 1, type: "getWorkspaceState" }`; synchronizes the current host projection.
- Webview → host `openFolder` / `manageTrust`: `{ version: 1, type: "openFolder" | "manageTrust", generation: number }`.
- Webview → host `chooseResources`: `{ version: 1, type: "chooseResources", generation: number, choice: "allow" | "decline" }`.
- Webview → host `sendChat` (WI-004): `{ version: 1, type: "sendChat", generation: number, text: string }`. `text` must be non-empty after trim and at most `8000` characters. Allowed only when `runtime === "ready"`, generation matches, workspace actions are not `busy`, `modelBusy` is false, and no chat turn is in flight.
- Webview → host `setThinkingLevel` (WI-008): `{ version: 1, type: "setThinkingLevel", generation: number, level: string }`. `level` must match the host-projected allowlist (`thinkingLevels`) and a bounded token shape. Allowed only when `runtime === "ready"`, generation matches, workspace actions are not `busy`, and `modelBusy` is false. `chatBusy` does not prohibit selection: while streaming, record next-turn intent without mutating the running model/thinking settings.
- Webview → host `setChatModel` (WI-008): `{ version: 1, type: "setChatModel", generation: number, provider: string, modelId: string }`. `provider` and `modelId` must match a bounded token shape and an entry in the host-projected `availableModels` list. Same eligibility as `setThinkingLevel`.

Rejected malformed messages receive no response. Stale or ineligible valid actions only resynchronize state. Ping has no business side effects. No action accepts a path, command, trust boolean or runtime request from the webview.

## Host state projection

The host sends `version: 1, type: "workspaceState"`. [`WorkspaceStateMessage`](../../src/extension/bridge/webviewMessages.ts) owns the complete field/type declaration; this table defines semantic groups. The UI renders this projection instead of inventing authoritative state.

| Fields | Meaning and limits |
|--------|--------------------|
| `generation`, `status`, `folder` | Nonnegative safe-integer generation; status is `no-folder`, `multi-root`, `remote`, `non-file`, `untrusted` or `eligible`. Folder is `{ name, path }` for one folder or null. |
| `choice`, `busy`, `error` | Choice is null/`allow`/`decline`; busy tracks unfinished workspace actions; error is null or a fixed bounded recovery message, without raw exceptions. |
| `runtime`, `runtimeDetail` | Phase is `not-started`/`starting`/`ready`/`stopping`/`error`; failure detail is a bounded host diagnostic or null, without raw exception dumps. |
| `messages`, `chatBusy`, `chatError` | Ordered host-owned `{ role: "user" \| "assistant", text, id? }` entries, with optional correlation id. Busy starts at submission and lasts until settlement/failure. Chat errors are bounded, without raw stderr or credentials. |
| `chatModel`, `thinkingLevel`, `thinkingLevels`, `availableModels` | Applied model label/level can be null; capability lists are bounded, with at most 64 `{ provider, modelId, label }` model entries. |
| `pendingModel`, `pendingThinkingLevel` | Null or a pending catalog entry/valid level; host-memory intent is distinct from applied values. |
| `modelBusy`, `modelError` | Catalog loading, serialized application and recovery block sends and further selections; failure text is bounded or null. |
| `activities`, `approvals`, `grants`, `execution`, `controlledExecution` | Execution projections defined below; `controlledExecution: true` identifies the profile, not readiness or gate acceptance. |

**Producer-side display bounds (WI-010 correction):** active model labels, including provider/ID fallback, are at most 200 UTF-16 units. Final assistant text/deltas are capped at 65,536 units after redaction; activity text/input at 16,384 after redaction, with truncation reported. Workspace alias labels are at most 512 units (ellipsis, no split surrogate); ineligible non-file URI labels at most 65,536. The actual native local cwd is never shortened. Trusted-entry display names are at most 512 UTF-8 bytes, code-point safe with ellipsis; the native consent dialog and host retain the full canonical path. The model summary keeps thinking separately visible, while title/accessibility text and the scrollable, wrapped current-model menu retain the full bounded label. These are producer/UI contracts, not secret-scrubbing guarantees for arbitrary intentional content.

## Controlled execution contract

Execution actions use the envelope rules above and these inbound shapes:

- `stopChat`: `{ version: 1, type: "stopChat", generation: number }`; only an active chat not already stopping is acted on.
- `decideApproval`: `{ version: 1, type: "decideApproval", generation: number, id: string, decision: "once" | "session" | "deny" }`.
- `revokeGrant`: `{ version: 1, type: "revokeGrant", generation: number, id: string }`.

IDs must be nonempty and at most 100 characters. Existing exact-own-field validation, active-view, generation and workspace-busy checks apply. IDs select host-owned pending requests/grants, never a webview-supplied command or path. Unknown/expired decisions cannot revive a removed request. `session` creates a grant only when a non-null reliable scope exists; absent scope provides no reusable authorization and UI must offer Allow once only.

Execution projection fields:

- `activities`: at most 64 host-owned `ActivityItem` entries: `{ id, kind: "thinking" | "tool", messageId, contentIndex?, toolCallId?, tool?, text, input?, status, truncated }`. Status is `thinking`, `preparing`, `executing`, `complete`, `failed` or `interrupted`. Thinking correlates by message/content index; tools by tool-call ID. Text and displayed input are bounded to 16,384 characters per item (bounded aggregate by item count). Text or input overflow sets `truncated`, retained across tool updates. The 64-entry cap reserves a stable `activity-overflow` notice: additional activity is omitted from display, not execution/approval checks. The UI renders truncation notices and incremental stable-ID details, preserving expansion/focus/scroll. `tool_execution_start` projects `preparing`, not side-effect confirmation. `partialResult` replaces cumulative output. `message_end` reconciles final text/thinking; no synthetic thinking when absent.
- `approvals`: at most 8 `{ id, toolCallId, tool, input, scope: string | null, expiresAt }` cards. `input` is the full JSON argument snapshot, at most 32,768 characters; oversized or credential-like inputs are denied before projection. Default host/gate timeout is 120 seconds. Denial, expiry, cancellation and late replies never confer approval.
- `grants`: at most 64 `{ id, scope }` entries. Existing regular-file scope encodes `[tool, canonicalPath]`; shell scope encodes `[tool, canonicalCwd, completeInput]`. Scope equality is exact; no implicit directory/command-prefix grants. Nonexistent/unresolvable targets have null scope. Inspect/revoke affects subsequent calls, not past effects.
- `execution`: `idle`, `waiting`, `thinking`, `awaiting-approval`, `executing`, `replying`, `retrying`, `compacting`, `completed`, `stopped`, `stopping` or `failed`; a presentation state, not evidence of sandboxing. `controlledExecution` describes the selected profile, not proof of runtime readiness or gate closure.

`toolApproval.ts` auto-allows only canonical in-workspace regular-file `read`. Search/list still ask, as do edits/writes, shell and external paths; unknown tools fail closed. Windows ambiguous paths are not auto-authorized; realpath checks cover symlink/junction escapes but cannot prevent check/use races. Same-live-session grants survive view recreation, ordinary settlement and successful Stop; workspace/eligibility change, runtime replacement/disconnect and provider disposal cancel requests and clear grants.

Host cancels pending approvals before `abortTask`; adapter cancels outstanding dialog waits, sends `clear_queue` then `abort` with bounded waits. Success requires settlement; failure or lack of settlement shuts down runtime and reports failure. Host keeps `stopping` through cancellation and delays pending settings application until it completes. Runtime loss marks unfinished activity interrupted; no automatic task replay. Stop does not undo side effects or guarantee cancellation of every descendant process.

The adapter accepts only the bundled gate's product envelope `protocol: "pi-vscode-approval", version: 1`, with runtime/cwd matching the current subprocess and `kind: "hello"` via notify before readiness. Calls carry `request`, `toolCallId`, `tool`, `input`; the bundled asynchronous `tool_call` handler waits via public `ctx.ui.confirm` and checks the full argument snapshot again after confirmation. RPC dialog IDs correlate `extension_ui_response`; title text is not authority. This is not a generic `approve_tool_call` RPC. The controlled tool allowlist is `read,write,edit,bash,powershell,grep,find,ls` with `--no-extensions -e <bundled gate>`; third-party extension discovery is disabled for either project-resource choice. Missing bundle blocks startup; missing hello/readiness terminates it, with no usable no-tools fallback promised. The offline load-failure fixture separately uses `--no-tools`.

Forward only bounded presentation fields, never raw RPC objects/stderr, signatures or credential stores. Pattern filtering is best-effort and cannot guarantee arbitrary thinking/tool output is secret-free. [Architecture §7](../architecture/vscode-extension-architecture.md) owns process permissions and environment controls; verification records are linked under Evidence boundaries below.

WI-021 projects public pi 0.86.1 auto_retry/compaction phases without owning their algorithms. Reliable agent_settled freezes the task as completed/stopped/failed; an explicit Stop/runtime failure freezes failed when settlement cannot be obtained, without rewriting an already reliable outcome. Unfinished Stop remains stopping. If task settlement precedes prompt ACK, delivery waiting remains separate: reject late phase/content events, and ACK must not rewrite the frozen outcome. Confirmed rpc-accepted/rpc-rejected/not-sent delivery does not become unknown after disconnection; uncertain delivery must never be replayed automatically.

## Deferred model/thinking settings (WI-008 / WI-009)

- Idle valid selections apply immediately. During `chatBusy`, selection only overwrites its own pending field (latest model and latest thinking independently win); no settings RPC runs during the active session-level run. The combined chip always shows applied values; a separate status shows `Next turn (pending)` / `Applying next turn`, including when the popover is closed.
- On the current runtime session's `agent_settled`, `applyPendingSettings` sets `modelBusy` before releasing the UI to send, applies `set_model` first, accepts its refreshed state/catalog/capabilities, and revalidates the pending thinking level before `set_thinking_level`. Unsupported or unapplied thinking produces a bounded error, not a silent clamp or fallback. The model may already have changed; this is not an atomic rollback transaction.
- Failure triggers one projection readback, not mutation retry. If readback fails, applied model/level and available levels are cleared instead of showing guessed success. Pending fields and `modelBusy` clear when the current application finishes; model errors remain visible outside the popover. Prompt rejection clears pending intent.
- Workspace identity/eligibility changes, runtime restart (including resource-choice changes), and provider disposal invalidate pending work. Generation, runtime session and catalog token prevent late completion from updating a replacement runtime. View replacement preserves host-owned pending/in-flight settings and resynchronizes the new view; old-view actions are rejected.
- Session completion uses `agent_settled`: no remaining automatic retry, compaction retry or queued continuation. `turn_end` or low-level `agent_end` is insufficient. Use the [pi integration guide](../guides/agent/pi-integration.md) for current-version and upgrade evidence; historical WI-004 observations apply only to their recorded version.

**WI-008 error and readiness boundary:** pi0.86.1 public get_state zero-capability unknown sentinel is not a configured model; a real model merely named unknown remains valid. No-model state gives configuration guidance and blocks Send. Provider error bodies are classified only inside the host, never forwarded verbatim: fixed authentication guidance for 401/403/missing keys, fixed availability/rate-limit guidance for503/429, and a fixed generic failure otherwise. A rejected public prompt RPC may carry allowlisted `rejection: "authentication"` in the internal adapter→host result; the host maps it to fixed text. This adds no Webview action/version, changes no rpc-rejected delivery fact and never retries or replays.

## Trust and lifecycle

- `PiChatViewProvider` owns the in-memory workspace identity, monotonic generation, choice and subscriptions. It observes folder changes and trust grants; every action re-reads actual workspace folders, `workspace.isTrusted` and `env.remoteName`. Remote hosts are blocked even with file URIs. Multi-root and non-file workspaces are blocked. Only a trusted single local file folder permits a choice.
- Workspace changes or eligibility changes reset choice and advance generation; repeated reads and view rebuilds retain choice. Extension-host reload resets everything. VS Code trust revocation reloads the window; the host also detects trust loss on every request. No settings, trust files, secrets or webview storage are used.
- `openFolder` is allowed only in an empty local window (`no-folder`). It opens a native single-folder picker, then rechecks generation and eligibility before calling public `workspace.updateWorkspaceFolders(0, 0, { uri: selected })` with the native file URI. Cancellation leaves state unchanged; a false return or exception shows a bounded retry / File > Open Folder recovery hint. A true return keeps the action busy until authoritative workspace change or host restart, preventing repeated updates; it is only request acceptance: the UI never fabricates a folder or successful state. Adding the first folder can restart the extension host without a folder-change event; the new provider constructor reads authoritative workspace state and starts with no resource choice. `manageTrust` is allowed only for an otherwise supported untrusted folder and invokes only `workbench.trust.manage`; it never grants trust itself.
- The editor-title navigation icon and Command Palette command `pi-vscode.focusChat` reveal the existing Pi container, then focus `pi-vscode.chat`; they do not toggle visibility or create another panel. The default remains `secondarySidebar`. The editor-title entry uses separate light/dark Pi SVGs; the Command Palette remains available when no editor title is shown.
- Native actions are serialized per active view. Pending work is invalidated on workspace change, view replacement/disposal or provider disposal. Results are checked again before subsequent commands or state updates. Failures show a fixed retry hint; cancel is not an error. Post failures are handled without leaking exception data; reopening the view resynchronizes.
- Allow/decline is editable and memory-only until workspace identity or eligibility changes. After a choice in an eligible workspace, the extension host starts pi in RPC mode with public `--approve` or `--no-approve` for that run only; changing choice restarts runtime. WI-010 replaces historical `--no-tools` startup with the controlled allowlist and exclusively bundled gate described above. Either choice disables third-party extension discovery; resource consent does not override it. Decline can still permit AGENTS.md context and other user/global resources per upstream docs. Neither is a sandbox or tool authorization.
- WI-004 chat: when `runtime === "ready"`, the host may send a bounded `prompt` over RPC and project `text_delta` events into `messages` until session-level `agent_settled`. The webview never imports pi, spawns processes, or sends arbitrary RPC. Transcript is memory-only; workspace identity/eligibility changes, runtime stop/restart or provider disposal clear `messages` and reject stale `sendChat` and late RPC events for prior runtime sessions.
- View listeners are disposed on replacement/disposal; workspace listeners on provider disposal. Each page gets a fresh script nonce and restrictive CSP. Names and paths arrive only in state messages and are rendered with `textContent`, never interpolated into HTML. Native buttons have clear text labels, keyboard activation and visible focus; state/errors use live regions.

### Ownership, eligibility and bounded capture

`DraftSubmission` owns the host draft, attachment preparation and submission ledger; `PiChatViewProvider` supplies execution eligibility and coordinates runtime/Stop/session transitions. `runtimeLifecycle.ts` owns the narrow internal prompt/result contract; adapter owns encoding, correlation and bounded writes; Webview owns presentation only. Use VS Code public document/picker APIs and host-only Node `fs/promises`/`path`, never Webview filesystem access, a generic bridge or pi session files. No new dependency, framework, process model or persistence.

- Add uses `window.showOpenDialog` with files only, single selection and current workspace as default. Cancellation is `cancelled`, not an error, and preserves the draft. Add is disabled while the one slot is occupied; remove then reattach explicitly. Require current trusted single local file workspace and ready controlled runtime. Recheck eligibility after every awaited boundary. No inferred open-file attachments.
- Before document loading, reject non-`file` URI, authority/query/fragment, nonabsolute or ambiguous Windows path (device/extended prefix, UNC, drive-relative, ADS, control characters, reserved device components, trailing dots/spaces). Resolve root and target with `realpath`; require a regular file and segment-aware `path.relative` containment, not a string prefix or blanket lowercase comparison. Check lexical and resolved path shapes; symlink/junction targets outside root fail. Record canonical root/target and stat identity (`dev`, `ino`, size, mtime/ctime); repeats must match. Unsupported/unresolvable identity fails closed. This is not an atomic filesystem lock or a malicious-workspace sandbox.
- Guard known credential sources **before loading**: any `.local-env` or `.ssh` component, `.env`/`.env.*`, `auth.json`, `credentials.json`, `id_rsa`, `id_ed25519`, and `.pem`/`.key`/`.p12`/`.pfx` files (case-insensitive component checks, both lexical and canonical). Never source SecretStorage, process environment or pi credential stores. After capture, reject recognizable private-key blocks or credential assignments using the existing credential-like key vocabulary (`api_key`, `authorization`, `password`, `secret`, `access_token`, with case/separator variants); no override or raw offending text in errors. This is conservative defense, not guaranteed secret detection in arbitrary code; UI warns users to attach only nonsecret code. All fixtures use dummy markers, never private files/keys.
- Check `stat` before `openTextDocument`: unopened disk file over **1 MiB** is `source-too-large` and is never opened/read by this feature. This acquisition ceiling allows common UTF-16/UTF-8 decoding overhead for a 256 KiB text snapshot; it is not the attachment budget. Reuse an already-open matching TextDocument (including dirty text) even if disk is larger, but still require existing regular-file containment. Before `getText()`, use `offsetAt` at the last line end to reject over **262,144 UTF-16 code units** without allocating the entire text; then enforce **262,144 UTF-8 bytes** on captured text. For unopened files, VS Code owns decoding/loading; its public API offers no hard read quota against concurrent file growth. Re-stat afterwards and reject changes/oversize; state this residual race rather than claiming bounded OS reads. No raw fallback read, automatic save or stale disk substitute.
- Text eligibility means a supported file successfully opened as a VS Code TextDocument; rejected/binary/unsupported opens become `not-text`. This is not an extension-based binary sniffer or a guarantee that arbitrary bytes are text. Empty text files are allowed with a nonempty user body. Record actual editor text, document object/URI, version and dirty flag. Change/close/reopen, rename/delete, changed canonical/stat identity, or a different final text invalidates the attached revision permanently until removal/reattachment—even if text is later restored. Observe document changes/close and revalidate on send; `DraftSubmission` owns and disposes its document listeners. Previews always show the captured snapshot, never silently refresh it.

### Versioned intents and safe projections

Migrate the **entire Webview envelope to numeric version 2** in the same slice: validator, all current UI senders/host projections and their tests. Existing actions retain their payload semantics except draft-based `sendChat` below; reject all version-1 actions rather than letting an old page bypass attachment admission. HTML and host ship together; old pages must reopen/reload, with no compatibility shim. Every v2 action other than bootstrap `ping`/`getWorkspaceState` adds `viewId` (host-issued opaque ID) beside existing `generation`; host still checks the actual view instance. Bootstrap replies bind current `viewId`. This does **not** change the distinct `pi-vscode-approval` gate protocol v1 or upstream RPC.

All objects use exact own data fields/no accessors. IDs are `[A-Za-z0-9_-]{1,100}`; revisions and offsets are nonnegative safe integers, never wrap/reuse. The common action envelope is `{ version: 2, type, generation, viewId }`; the following lists **all additional fields**:

- `updateDraft`: `{ draftRevision, editSequence, text }`; text at most **8,000 UTF-16 code units before trim**, empty allowed for editing. One update in flight; UI retains only the latest local edit while waiting. Host requires matching base revision and increasing view-local `editSequence`, stores text, advances revision and returns accepted sequence. Send waits for latest edit acknowledgement. No attachment text/path is accepted from UI.
- `addFileAttachment`: `{ draftRevision }`; `removeAttachment`: `{ draftRevision, attachmentId }`; `sendChat`: `{ draftRevision }`. Host retrieves body/attachment itself; body must be nonempty after trim and stays independently 8k-bounded. Plain-text sends retain trimmed-body behavior and upstream command handling; enriched sends use the encoding below. Each mutation advances host revision; late/duplicate base revisions only resynchronize.
- `getAttachmentPreview`: `{ requestId, snapshotId, offset }`; offset is a UTF-16 boundary in a current draft or retained submission snapshot. One active preview response per view, no pending queue; excess valid requests get `busy`. Fixed maximum chunk **16,384 UTF-16 units**, at most **49,152 UTF-8 bytes**, avoid splitting surrogate pairs; next offset is host supplied. Full preview is optional and sequentially assembles at most one 256 KiB snapshot in the UI.
- `getAttachmentHistory`: no additional fields. Returns the complete bounded metadata list, not bodies; thus every retained snapshot remains reachable even after its chat row leaves the 32-message projection. No pagination subsystem in this slice.

Dedicated `attachmentState` (v2, current generation/viewId) contains `draft: { revision, text, acceptedEditSequence, attachment }`, `preparation: "idle" | "picking" | "preparing"`, `result: null | { code }`, `historyCount`, `retainedBytes`, and `lastSubmission: null | { submissionId, draftRevision, delivery, outcome }`. `attachment` is null or `{ attachmentId, snapshotId, relativePath, kind: "file", utf8Bytes, unsaved, state: "attached" | "changed" | "unavailable" }`. No absolute source paths/document objects/stat data enter attachment DTOs. Metadata path is at most **1,024 UTF-8 bytes**; oversized metadata rejects capture, not silent truncation.

`attachmentHistory` adds `entries` of `{ submissionId, snapshotId, relativePath, kind: "file", utf8Bytes, unsaved, delivery, outcome }`; maximum **128 entries**, each serialized metadata object at most **2 KiB UTF-8**. `attachmentPreview` contains `{ requestId, snapshotId, offset, nextOffset, done, text }` or `{ requestId, code }` (discriminated by presence of `code`); full serialized response including envelope is at most **128 KiB UTF-8**. These safe text DTOs render with `textContent` only, never HTML, Markdown or executable links. View/snapshot/request mismatch discards replies. State/history refresh only on relevant changes/request/recreation, not every streaming delta; at most one assembled preview is kept, replacing/closing it frees its text.

Codes are exactly `cancelled`, `busy`, `stale`, `ineligible`, `slot-full`, `invalid-source`, `outside-workspace`, `unavailable`, `not-text`, `source-too-large`, `text-too-large`, `metadata-too-large`, `sensitive-source`, `source-changed`, `history-full`, `frame-too-large`, `preparation-cancelled`, `write-failed`, `ack-timeout`, `rpc-rejected`, `runtime-lost`. Malformed envelopes remain ignored without response/effect; valid obsolete actions return current state with `stale`. UI maps codes to fixed recovery text (at most 300 characters), never exceptions/content. Source/budget failures preserve the draft and offer remove/reattach/reduce; history-full offers inspect history or deliberately end/restart the live session with loss warning; transport uncertainty offers Stop/restart guidance, never automatic retry.

### Draft transaction, delivery and lifecycle

1. Host owns acknowledged body and attachment across view recreation. New view gets fresh `viewId` and current revision before editing; local newer unacknowledged text is not overwritten by an old acknowledgement. UI clears only on `lastSubmission.draftRevision` matching the submitted revision **and** unchanged local edit sequence; new edits are subsequently synchronized as a new revision. Changes during preparation invalidate its token and preserve the newer draft. An edit never received by host cannot be promised after view loss; UI labels synchronizing/unsynchronized state and does not claim it is saved.
2. Serialize one picker/preparation and one submission. Capture preparation token, draft revision, workspace generation, runtime session and current view. Perform bounded async source checks; recheck every identity after awaits. At final synchronous boundary verify document object/version/open status/text/dirty flag, body/attachment budgets, metadata, eligibility and cancellation token; reserve history capacity, construct one immutable submission, serialize and validate the actual outbound frame **before admission**. No asynchronous file reread after freezing. This guards host/editor consistency, not future runtime tool reads or check/use races.
3. Admission atomically commits the immutable snapshot plus body, advances/clears only that draft revision and marks delivery `host-accepted`; history and prompt take the same frozen data. Call the adapter immediately within the same synchronous turn; adapter checks expected session and consumes its one-attempt token before handing bytes to stdin. `write-attempted` is published at that boundary, `rpc-accepted` only on matching successful response, `rpc-rejected` only on an explicit negative response, `not-sent` only when no write was attempted, and `unknown` on write/ACK/loss uncertainty after an attempt. No reinsertion of a possibly sent draft and no automatic resend. Keep even rejected/uncertain submitted snapshots for inspection, accurately labelled—not all are “sent successfully”.
4. Task outcome is independently `pending | settled | failed | interrupted`; matching `agent_settled` is the existing settlement boundary, not the prompt ACK. Early streaming/settlement before ACK must not regress outcome or allow a second admission while ACK remains unresolved. Host acceptance or write/drain is not remote acceptance/completion.
5. Stop during picking/preparing invalidates token, yields `preparation-cancelled`, preserves draft and guarantees zero prompt writes. After write handoff, use existing controlled Stop/clear_queue/abort; remote effects may already exist. Stop never sends drafts, restores uncertain submissions or replays them. View disposal cancels uncommitted picker/preparation/preview but preserves acknowledged draft and admitted history; a committed attempt continues host-owned. Old-view events cannot mutate the replacement.
6. Workspace/trust/eligibility or runtime replacement invalidates attachment eligibility and async work; retain body with an invalidation notice, remove source capability, require deliberate reattachment, and never silently carry context to another project/runtime. Live history ends only with its owning session: disclose memory-only loss on deliberate restart/resource-choice change; fault loss reports history ended, not persistence. Host reload/provider disposal releases all snapshots, subscriptions, timers and preview references. A same-session successful Stop retains history. No new session persistence or automatic reset.

**Delivery/settlement recovery:** an explicit RPC rejection ends the waiting execution state as failed and offers configuration inspection before a deliberate new submission, not an unavailable Stop action. If settlement precedes the ACK, admission remains blocked until the ACK resolves, then the same settlement projection completes the turn. A late ACK cannot overwrite runtime-failure/interrupted state. A valid Stop received after settlement still republishes current state so a renderer cannot remain locally stuck in stopping.

### Encoding, transport and memory budgets

Installed and declared pi are **0.86.1** (read-only inspection, not runtime evidence). Its public `docs/rpc.md` and `dist/modes/rpc/rpc-types.d.ts` define `prompt.message`, images and streaming behavior, **not** an RPC `expandPromptTemplates` option. Do not invent that RPC field from an SDK option or import private types at runtime. For attachment submissions construct `message` as the fixed non-slash ASCII prefix `User task with explicit untrusted file context. JSON data follows:\n` plus `JSON.stringify({ body, attachment: { path, kind: "file", unsaved, text } })`. This makes the entire prompt non-command-leading; body/file slash/template text stays JSON data, with delimiters/control characters escaped. Verify literal template/skill-command fixtures in the later authorized real-runtime check; no assertion that labeling defeats prompt injection. No-attachment prompts keep existing semantics.

- Body raw length ≤8,000 UTF-16 units, attachment text ≤262,144 UTF-8 bytes, path ≤1,024 UTF-8 bytes. Fixed prefix/JSON keys, boolean, punctuation and RPC envelope/ID must occupy at most **1 KiB** before escaping. Adapter receives a discriminated host-only plain/enriched prompt input and independently checks the body and attachment caps plus serialized frame; do not bypass the 8k body validator with an arbitrary large `prompt(string)` path.
- Analytical conservative bound, not an executed test: JSON can expand a one-byte ASCII control to six ASCII bytes; nesting that JSON inside RPC can at most double those bytes. Text contribution ≤`12 × 262144 = 3,145,728`; body ≤`12 × 8000 = 96,000` (lone-surrogate escapes also fit); path ≤`12 × 1024 = 12,288`; allow `12 × 1024 = 12,288` for fixed overhead. Sum **3,266,304 bytes < 4,194,304**. Still measure `Buffer.byteLength(serializedFrame, "utf8")` before every actual write; this proof is for one file, not the final 1 MiB multi-file target. Existing receive cap of 8 Mi characters is unrelated.
- No attachment write queue: one prepared frame, one write attempt. Register response/stream error/close handlers before write; absent/closed stdin or a serialization failure before invocation is not-sent; a throw/error once `write` is invoked is conservatively unknown, including callback error. Wait for successful write callback and, if `write()` returned false, `drain`; allow an early correlated ACK but do not leak listeners or reorder a later prompt. **5 seconds** for local write/drain, **30 seconds** total ACK deadline from write invocation (not an additional 30 seconds). On timeout/error/loss clean listeners/timers/pending response, fail current runtime through the existing failure/shutdown path, no retry. Stop control writes retain their existing bounded cancellation semantics and must not wait behind a product queue of attachments. Tests must exercise ACK before callback/drain, close without drain and Stop racing write. No claim of remote delivery from local flush. Transport-loss cleanup binds the captured child identity even after session invalidation; shutdown detaches it before awaiting closure so late callbacks cannot terminate a replacement. SIGTERM escalates after 5 seconds; absence of observed closure after another 5 seconds reports unconfirmed shutdown and blocks replacement until manual cleanup and host reload.
- Retained live submissions have **8 MiB total UTF-8 logical payload** (body + attachment text + serialized immutable snapshot metadata: submissionId, snapshotId, relativePath, kind, utf8Bytes and unsaved). Delivery/outcome are bounded record-state overhead, not logical snapshot payload, **128 records maximum**. Reserve exact charge before admission; no silent eviction or perpetual global quota—capacity resets only when the live session ends, with disclosed loss. The record cap bounds empty/tiny-file metadata and allows history beyond 32 visible messages; the byte cap allows many full-size snapshots without unbounded growth. Whole bounded history list is accessible from an explicit “Attachment history” control from the first slice; T014-05 improves navigation, not basic access.
- Memory is separate from wire size: retained strings have a conservative **16 MiB UTF-16 content ceiling** under that 8 MiB charge, plus bounded 128-record/object overhead (not a heap-size guarantee). One draft ≤256 KiB text plus 8k body; one preparation snapshot; one ≤4 MiB UTF-8 outbound buffer with transient serialized strings released after write; one preview chunk and one UI assembled preview ≤256 KiB UTF-8. Do not cache duplicate serialized prompts per history entry or include history bodies in every workspace projection. Overflow blocks new attachment sends but not plain chat, Stop or inspecting retained data.

Answers are exact discriminants: `{ method: "select", optionId }`, `{ method: "confirm", value: boolean }`, or `{ method: "input" | "editor", text: string }`. The host validates method, current active membership, exact option membership and UTF-8 budget before reserving a reply. Empty strings are preserved, not coerced into cancel. Options use host opaque IDs and map to original strings only inside the adapter.

`interactionState` projects an active form or null, queued count, phase (`idle | waiting | blocked`), bounded fixed error code, bounded literal feedback and omitted-feedback count. Forms share opaque id, method, title and an optional explicitly labeled local cutoff timestamp; select adds option IDs/labels, confirm adds message, input adds placeholder, editor adds prefill. Origin is explicitly “trusted runtime extension; not authenticated”, not inferred from a title. No remote-consumed/closed/completed field is fabricated. A separate `executionProfileState` projects controlled/trusted display label, phase (`idle | selecting | switching | recovery-required | error`), fixed failure code and booleans for currently admissible named actions. Host remains authoritative; Webview state never clears a recovery fence.

Standard feedback is literal: notify, keyed status and string-array widgets are presented; requested terminal title/editor text are displayed as labeled feedback, never executed as title commands or silent draft replacement. Custom/component TUI, editor readback and arbitrary terminal layout remain unsupported and visibly disclosed before loading. Retain at most 16 feedback entries, 65,536 aggregate UTF-8 text bytes and 32,768 bytes per entry; keep at most eight status keys and four widget keys, each key at most 100 bytes. Keyed updates replace their prior entry; clears remove it. Capacity discards oldest feedback with an omission count, never an actionable form/answer. Oversized or credential-like content yields a fixed safe warning, not raw text. Widget placement is a hint only; content remains accessible in the extension feedback region. Feedback is not dialog completion evidence.

### Arbitration, timing and lifecycle

Host coordinator owns one active plus seven FIFO queued forms and current view projection. Adapter owns private remote IDs, exact connection-lifetime replay retention and one-shot reply capabilities. Reserve/invalidate synchronously before any asynchronous write; a later Stop/loss suppresses an unattempted affirmative write, with no retry after uncertain delivery. Host/view/runtime replacement invalidates old answer authority before cleanup. Recreating only the Webview resynchronizes the same host ledger with a new viewId; no timer/request replay. Validation has no side effect on invalid/stale/duplicate input. Declining a form may continue extension code and must be labeled separately from Stop.

Use the selected numeric budgets in ADR 0002. The existing general RPC frame/partial-buffer boundary remains separately enforced; general-stream overflow/loss must not become a fake interaction exit or auto-kill incompatibility workaround. Valid remote timeout duration is finite, nonnegative and at most 86,400,000 ms; larger/invalid duration is an explicitly unsupported request, not silently shortened. Local receipt-based cutoffs invalidate active or queued entries once and cannot prove when upstream expired. A no-timeout form can wait indefinitely for a human. During trusted startup, admitted unanswered forms pause only the remaining 15-second readiness-response budget; after their reply writes finish, that remaining transport budget resumes. This does not infer handler completion or extend the separate Stop observation budget. Reply transport permits at most 16 in-flight writes, shares bounded stream listeners, and requires both write callback and drain within five seconds; capacity or uncertain write failure blocks the connection without retry or automatic termination. A known exact extension-command handler lease has no human-response ACK timer; a five-second bounded write deadline remains. Ordinary prompt transport/admission limits remain distinct. Matching handler response releases only that handler lease; errors, agent work, outstanding dialogs and queues remain independent obligations. An unknown/misformatted slash command is never classified as that lease merely because one prompt is pending.

Stop first closes admission and invalidates/cancels all still-unanswered forms and covered approvals, including a cancellation-triggered next form, then clears the public queue and requests abort. Observe separate handler/agent/dialog obligations for five seconds. No evidence by the deadline means stop-unconfirmed/recovery-required; disable sending, profile/session/model transitions and answers, retain available draft and show terminal/manual-end guidance. No automatic task replay or kill. Detached extension work is not claimed settled; reliably incompatible operations are excluded or the extension is excluded when separation is unavailable. Explicit End owned runtime and controlled recovery follow the persistent exact-child contract in ADR 0002, not an arbitrary PID action. Pending startup, error, stream loss, host loss, observed child exit, never-spawned failure and successful receipt retirement remain distinct. Cleanup of the retained exact run remains available when workspace execution is ineligible (restricted, no-folder or multi-root); it never grants trust/resource consent or bypasses startup eligibility. See the WI-010 cleanup correction in ADR 0002.

## 回答步骤

1. **识别请求。** 区分判断、提案、执行与明确的头脑风暴，并核对已有授权。只读问题以回答为完成条件；明确的实施请求按已批准范围完成工作。
2. **核对证据。** 按内核基础阅读及任务路由，读取 ACTIVE 和相关需求、Gate、代码或验证记录。分别标记观察、推断与未知；完成条件是每个事实结论有可引用依据，缺证据处有具体核查动作。
3. **作出判断。** 先答可以、不可以、部分成立、尚未完成或未知，再给决定性证据及必要下一步。当前阶段无需新增工作也是有效结论。
4. **记录交接。** 产品取舍归维护者，调查与方案归 Agent；按[协作 §7](../agent-collaboration.zh.md#7-agent-义务)保存值得跨会话保留的结论。记录想法不授权实施，不创建并行 WI。

## 按问题应用

| 问题 | 回答完成条件 |
|------|--------------|
| 还需要优化吗？ | 将实际缺口与当前 WI 验收对照；没有必要改动时明确说明。只有明确要求备选方案／头脑风暴时才列可选项。 |
| 请头脑风暴 | 给出明确标为可选／延后的想法，区分探索与承诺；记录按协作指南处理。 |
| 测试过了，算交付吗？ | 分别核对技术验证、批准切片、所需人工验收及适用 Gate；只对证据覆盖的范围声称完成。 |
| 宿主支持这个集成吗？ | 用公开 API 或受控 spike 支持结论；缺少验证时说明未知及最小核查步骤。 |
| 这个功能已经有了，对吗？ | 核对当前实现和验收，指出准确成立的部分及限制；不用历史脚手架示例代替当前事实。 |
| Draft PRD 以后会补吗？ | 检查 Prepare→Build 的 PRD 判定与切片提案；缺少触发点时指出缺口，不保证自动补全。 |
| 可以按归档设计实现吗？ | 对照当前权威和批准范围；旧设计有价值时作为变更提案，不能以历史细节直接授权实现。 |
| 下一步做什么？ | 从 ACTIVE 的 WI、阶段及未决条件给出建议；没有批准的新范围留在 Prepare。 |
| 我理解对吗？ | 对确切主张回答是／部分／否，附证据与缺少的条件。 |

## 证据边界

示例只规定判断方法。WI 状态、版本和验收均从当次文件与检查取得；未运行的检查保持未验证。维护者的批准不能替代事实证据，Agent 的建议或测试通过也不能替代产品决定、Gate 接受或明确提交授权。

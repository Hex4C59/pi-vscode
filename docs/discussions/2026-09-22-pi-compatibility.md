### Attachment feasibility and proposed validation seam

Keep REQ-003's agreed UTF-8 budgets and separate user-body bound. Actual current limits differ by channel: `chatBounds.ts:1–2` and validator `webviewMessages.ts:88–91` limit the body to **8,000 characters**; `toolApproval.ts:57` limits approval input to **32,768 characters**; assistant projection caps at **65,536 characters**, not attachment capacity. WI-013's 32/64 KiB values in the Planned contract are unapproved interaction candidates, not existing global ingress limits. `src/adapter/runtime/jsonl.ts:4–7,21–31` has no outbound size check and bounds received JSONL at **8 Mi characters**, not UTF-8 bytes. `pi-rpc-runtime.ts:305–334` sends one JSON-escaped prompt with a 30-second acknowledgement wait, without write/drain handling. None proves that the proposed 1 MiB attachment payload works end to end.

Propose host-owned snapshots and metadata-only, exact-shape attachment intents using opaque IDs, not Webview-supplied paths/text. Send body remains separately bounded. Compose immutable validated text into public `prompt.message` with relative source/kind/original-range/unsaved metadata and explicitly delimited, escaped, **untrusted context**; no execution authority arises from delimiters, and they are not a prompt-injection sandbox. Freeze encoding and versioned attachment contracts before Build in the existing reference, including leading slash/template expansion behavior so attachment text cannot accidentally become a command. No raw RPC pass-through or new upstream attachment field.

Budget independently the serialized outbound prompt (JSON escaping, metadata and body overhead), on-demand preview chunks, bounded retained snapshots and compact state projections. Do not enlarge approval, assistant or generic ingress limits to fit attachments. Use a dedicated bounded context path and flow control, retaining full actual-sent text in the live-session snapshot store and exposing preview on demand rather than resending megabytes with every delta. Concrete byte/frame/chunk/retention numbers and overflow navigation remain proposed technical design work; the agreed product attachment caps are not reopened. If capacity cannot meet those caps, block that implementation claim rather than silently truncate. Live-session retention must not silently evict snapshots with today's 32-message projection; bounded storage needs visible backpressure/recovery, not unbounded history or a new persistence promise. Persisted history and restoration remain REQ-008/public APIs, outside WI-014.

Highest practical seam: host intents through the injected VS Code/document API and captured `PiRuntimeLifecycle.prompt` payload (`src/extension/tests/harness.ts`, `runtime-chat.spec.ts`). Add deterministic fixtures for document versions/dirty snapshots, add/remove/preview, current-file reconfirmation and stale-selection choice; assert exact submitted text/metadata, no save/disk fallback, zero send on failure and cleanup. Extend strict-validator tests for forged IDs/extra fields/stale view/workspace/runtime. If adapter framing/write behavior changes, test real serialization/fragmented LF reads, UTF-8/JSON expansion, overflow and lost acknowledgement without retry. Reuse the VM DOM seam in `execution-ui.spec.ts` (`execution UI keeps incremental nodes, expansion, focus, scroll and cumulative output`; `Stop stays visible through stopping, locks approvals, preserves drafts and next-turn controls`) for literal previews, keyboard actions, errors and stable streaming. Tests and seams are proposed, not implemented or run. Later F5 and installed Windows VSIX must verify real editor snapshots/transport/preview responsiveness; Cursor evidence is separate.

### Requirement boundary and actual gaps

REQ-004/005/009 require honest observable state, local invalidation and stale-answer protection, bounded interactions without extending explicit deadlines, and supported-operation Stop or explicit unconfirmed failure. They do **not** require universal cancellation of arbitrary JavaScript, a sandbox, globally immutable/authenticated source identity, exact synchronous cross-process form closure, or a separate ACK for every answer. Lifecycle events and response outcomes below are **candidate mechanisms**, not newly confirmed product requirements. In particular, earlier wording treating “strict expiry/source/end guarantees” as the only alternative to weakening the PRD was too strong and is superseded here. Honest delayed observation can preserve the chosen product direction; feasibility and acceptance still need evidence.

The established pi 0.86.1 evidence below distinguishes five gaps: (1) local adapter/host bookkeeping and passive child-exit exposure can be improved here; (2) inbound UI lacks operation/source context; (3) private timeout/signal closure and answer-consumption outcomes are absent; (4) prompt response is not general operation success, and idle command `ctx.signal` is generally undefined, not a universal Stop signal; (5) reload loses the owned child handle. IDs fix correlation only after an operation actually has an owner; they cannot make untracked work tracked. The current gate envelope is not authenticated against arbitrary co-loaded extensions; adding another envelope does not fix that boundary.

### Three paths and recommendation

1. **Local adapter/host ledger — necessary foundation, insufficient alone.** This repository owns validated DTOs, one-shot local answer eligibility, view/runtime generations, bounded queue/diagnostics, cancellation ordering and distinct child-exit evidence. Cost is contained but touches host/adapter/UI lifecycle tests. It interoperates with unmodified 0.86.1 and preserves truthful unknown outcomes; it cannot synthesize remote closure, source or operation settlement. - **Dialog lifecycle:** proposed `ui_opened` includes scoped IDs, method, bounded payload and optional runtime-owned deadline metadata. `ui_closed` carries the same IDs, terminal revision and exactly one reason: `answered | user-cancelled | timed-out | signal-aborted | operation-cancelled | operation-failed | session-ended`. Detached/unregistered work is `unknown/untracked`, never silently covered by a handler return. A caught handler exception must yield a failed scoped outcome, not prompt-success inference. Arbitrary JavaScript cannot be preempted, and noncooperation remains unconfirmed failure, not a fabricated cancelled event.
- **Ordering/loss:** runtime emits a monotonic `eventSeq` for the negotiated stream; open follows start when a tracked parent exists, terminal outcome/close share one arbitration revision, and registered dialogs/children close before scoped settlement. Host tolerates identical duplicates, rejects conflicting duplicates and fails the affected scope closed on gaps/out-of-order terminal facts rather than guessing. Finality is irreversible. Disconnect invalidates local answers; remote outcomes remain unknown. No transparent reconnect/resend of commands or answers in v1: a new connection needs explicit recovery and fresh IDs. View-only recreation resynchronizes the same host ledger. Host reload loses ledger/handle: new readiness does not clear old-work uncertainty, and this recovery branch remains blocked until an approved observable boundary exists.

#### Timing and evidence strength

- **Upstream timer:** `createDialogPromise` checks already-aborted signal first (then emits no request), registers an abort listener and schedules `setTimeout(opts.timeout)` before registering/outputting the request. The relative milliseconds are not measured from host receipt or sidebar visibility. Serialization, stdout buffering, transport, host parsing/event-loop scheduling, Webview delivery and waiting behind another form consume time; answer serialization/stdin scheduling consumes more. No timestamp or shared monotonic clock is exchanged. Truthy timeout handling also means arbitrary numeric input must not be normalized into invented guarantees; a candidate supports only reviewed positive finite timer values within Node's effective range.
- **No exact deadline reconstruction:** let upstream scheduling occur at real time S, host receipt at R and declared duration be D. The nominal target S+D is no later than R+D, but unknown transit time means no positive remaining answer window is guaranteed at receipt. R+D is only a latest nominal estimate, not a bound on actual timer callback execution: event-loop stalls can delay upstream cancellation. A host monotonic timer avoids local wall-clock jumps but cannot synchronize upstream clocks or prove remote expiry. Do not label R+D an authoritative `expiresAt`, restart it on dequeue, or infer that an answer before it was accepted. Strict immediate closure on upstream expiry is unavailable even for `/timed`.
- **Private signal:** abort removes the pending entry and resolves the dialog locally in pi, without a wire close event. `/timed-signal` demonstrates a deadline not present on the wire. Missing `timeout` therefore does not prove indefinite upstream validity. Editor has no public signal/timeout options, but transport/operation loss still invalidates host answers. No blanket human timer is introduced.
- **Reply delivery:** a local successful write/callback or drain establishes only local transport progress, not upstream receipt or pending-ID lookup. The response handler silently ignores missing IDs and emits no acknowledgement for either consumption or ignore. A timeout may win before the answer arrives. Removing an answered form is a host transition, not evidence of accepted choice; never show “confirmed by extension” from write success.

#### Host-known lifecycle classifications

1. **Certain local facts, no remote-end claim:** validated receipt; local queue/admission; answer or cancel intent; one reply attempt; local invalidation by Stop, overflow, generation change or policy deadline. Disable answers atomically before I/O, remove invalid entries from the active queue, and retain a bounded explanatory status. Stop disables all active/queued answers. An ordinary cancel may resume extension code. Local invalidation is irreversible for that identity.
2. **Certain owned-process fact:** observed exit of the exact spawned child invalidates every request of that runtime, including buffered requests received afterwards. Distinguish actual child exit/close from spawn failure, stream error or disconnection; close after a spawn error is not proof that a process ever ran. It does not prove descendant termination, side-effect rollback, or successful operation completion. Current adapter combines these paths (`src/adapter/runtime/pi-rpc-runtime.ts:185–195`); separate passive observation is a future capability, not implemented evidence.
3. **Restricted inference only:** a correlated prompt response can witness the reviewed command handler's awaited chain has settled in this pinned implementation (`dist/core/agent-session.js:943–949,1062–1083`; `dist/modes/rpc/rpc-mode.js:298–319`). It cannot distinguish successful handler return from a caught exception by success flag alone; preserve `extension_error` as failure, and never interpret an uncorrelated error as successful completion. Detached work, hooks or timers defeat whole-operation completion. Lost prompt response remains unknown; do not retry the command. The adapter's current 30-second response wait is not a human-answer timeout and needs separate redesign before indefinite dialogs could work.
4. **No usable completion evidence:** notify/status text, a different dialog, `get_state` idle, `agent_settled`, `clear_queue` or abort ACK do not close an arbitrary extension operation. Notifications have their own IDs and no source/parent even within the same runtime; text matching is not correlation. Transport loss invalidates local answers but leaves remote execution unknown. Host reload loses the child handle and ledger; a new generation rejects old answers but does not prove the old process exited. Manual confirmation/PID absence checks alone are insufficient recovery evidence; until an approved observable recovery boundary exists, this branch stays blocked.

#### Minimal proposed state and acceptance (not a schema approval)

Keep three independent facts, rather than one overloaded `completed`/`cancelled` flag:

- **Host ledger:** opaque interaction ID mapped privately to upstream request ID, workspace generation/runtime instance, optional operation association with explicit basis (`reviewed-fixture` or `unknown`), method, validated payload and view revision. State is `queued | active | invalidated`; answer eligibility is host-owned. Upstream ID/source guesses never confer authority.
- **Evidence:** local invalidation cause (`answer-attempted`, `user-cancel`, `stop`, `local-deadline`, `overflow`, `runtime-lost`, `runtime-exited`, `generation-replaced`, `reviewed-handler-settled`); reply attempt `none | written-locally | write-failed`; remote outcome remains `unknown` unless separately evidenced. Handler state `pending | settled-under-review | failed | unknown` and runtime state `connected | lost | exited` are separate. Do not manufacture an upstream close reason or an `accepted` state. Local timer bookkeeping stays host-side and is not a remote expiry timestamp.
- **Webview projection/intents:** bounded method-specific form, opaque ID/generation/view revision, queue count and `canAnswer`, plus bounded status explaining “answer sent; acceptance unconfirmed”, “answering disabled; upstream state unknown”, or “runtime exited; interaction unavailable” as supported by evidence. Named answer/cancel intents select this ledger entry, with exact field, method, option-membership and string-budget validation. A false confirm answer is distinct from cancellation intent even if upstream returns false for both. No raw RPC, arbitrary command or inferred extension identity.

Proposed UX removes the editable form after local invalidation while retaining the reason; it does not silently erase uncertainty or display “upstream cancelled.” For timed queued requests, use the original receipt-based *local policy cutoff* if that policy is approved, check again before activation/reply, never grant fresh D on dequeue, and expire locally without approval/default answers. This only bounds stale presentation; it cannot satisfy exact upstream deadline semantics and is **not adopted as a substitute** for the confirmed requirement. A form can be disabled before its stale projection disappears; the host check remains authoritative. View recreation resynchronizes host state, not new upstream validity.

## Product direction (agreed)

Provide a local IDE agent workflow close to Claude Code / Codex, using **pi as the runtime**. Prioritize context input, task execution, process control, change review and session continuity, rather than reproducing vendor cloud services. The extension presents and orchestrates documented pi capabilities; it does not reimplement the agent loop, providers or session format.

**Confirmed clarification (2026-09-22):** build this VS Code plugin without modifying pi agent core, on the standard released pi baseline and documented public APIs. Support adding/loading custom **pi extensions**, both existing extensions and extensions written by AI; this is not a promise to host arbitrary VS Code `.vsix` extensions. Upstream enhancements are optional future improvements, not a prerequisite for this project or its baseline delivery. Evaluate a feasible scoped approach on the currently declared release before proposing an upstream dependency. There is no intrinsic requirement for every external extension to adopt a plugin-specific protocol, nor a promise that every extension or unchanged custom TUI works.

Keep Explorer on the left and prefer the secondary sidebar for chat. Optional editor tabs do not imply changing the default layout. Reference clients inspire observable workflows, not pixel parity or unsupported security promises.

### REQ-001 — Project and trust visibility

Show the active workspace folder before running a task. With no folder, explain how to open one and do not start a project task. Unsupported multi-root cases receive a clear explanation rather than silently selecting a folder. On workspace changes, do not silently continue the old task in the new project.

Distinguish VS Code workspace trust, pi project-resource trust and tool approval. Per confirmed D-03, do not start the agent in a VS Code untrusted workspace; do not silently trust pi project resources. When VS Code trusts the workspace but pi resource trust is declined, allow the session to continue with a visible indication that project-local pi resources are not loaded. This does not prevent ordinary project-file reads or imply that all context files and user/global resources are excluded; verify the exact pi loading boundary before implementation. Never describe resource trust as filesystem/network isolation.

### REQ-003 — Explicit editor context

Allow users to attach workspace text files or selected code, preview the exact context and remove it before sending. Whole-file attachments read the latest editor contents at send time. Selections capture a fixed snapshot at attachment time, with source path and original range; if the source document changes, require reattachment or explicit confirmation to send the old snapshot. Never present old line numbers as current locations. Sent historical attachments retain the content actually sent.

Unsaved editor snapshots are allowed, clearly distinguished from disk contents; never save automatically. Explain unavailable/deleted files instead of silently substituting stale disk content. Do not automatically attach unrelated open files. Images, PDFs, recursive directory and external-path attachments remain deferred. Confirmed candidate limits are 256 KiB per attachment, 1 MiB aggregate per message and 20 attachments, measured as UTF-8 bytes of the actual attachment text. The user message body retains its separate limit. Check on attachment and again against final content at send time; any excess blocks the whole send with actionable reduction/removal guidance, never silent truncation or omission. These product limits still require transport/rendering validation and do not guarantee sufficient model context.

Show compact attachment entries with relative path, whole-file/selection kind, original selection range, size and unsaved/stale snapshot state, with removal and optional complete text preview. Do not require opening every preview. If a whole file changes after attachment, pause sending, update its state and require explicit confirmation to use the latest contents; another change requires revalidation. Confirmation does not require reading the full preview. Selection snapshots retain the explicit stale-snapshot choice above.

### REQ-005 — Stop and recovery

Provide a stop-all action that clears queued continuation and requests cancellation of active work. Show stopping until the runtime settles or a shutdown failure is reported. ### REQ-006 — Execution approval strategies

**Two independent policy dimensions (confirmed 2026-09-22):** extension loading policy determines built-in-only versus explicitly trusted third-party loading; tool approval policy determines asking versus skipping covered approval prompts. This target retains asking, including Allow once and exact-scope live-session grants; skipping is deferred, not permanently rejected. Trusted extension loading retains approval for covered tool calls and never approves a pending call automatically. Extension-internal execution may bypass that coverage and must remain visibly disclosed. These concepts do not require two UI switches. In the profile descriptions below, controlled means built-in-only plus asking, and trusted means explicitly trusted loading plus asking; neither is a sandbox.

The revised target distinguishes **Controlled execution** (default) from **Explicitly trusted extension execution**. New or restarted runtimes start controlled, without third-party extension execution; loading trusted extensions requires explicit confirmation and visible coverage warnings. Project-resource consent is not extension execution consent. Trusted extension execution is not equivalent to the historical proposal to skip all per-tool approvals: it acknowledges executable extension code outside covered tool calls, not a universal authorization or sandbox guarantee. Controlled tool policy and grant scope retain the approved D-01/D-02 and WI-010 boundaries.

Switch execution profiles only while idle. If work is running, require an explicit Stop and wait for settlement first; never replay the task or undo completed changes. Preserve saved dialogue and unsent drafts across a switch, clear temporary tool grants, and do not promise to preserve extension-internal transient state. Whether switching requires runtime reconstruction remains a technical question. On switch failure, enter an unready state, preserve dialogue/drafts and block sending; recovery requires the user to retry or restart controlled execution. No silent fallback, task replay or claim that extension-initialization side effects were rolled back. This profile rule does not alter WI-008/WI-009's next-turn model/thinking selection.

For a covered approval-required call, do not execute before approval. Show the tool, target/command and meaningful input. Rejecting, dismissing or timing out must not approve it. Stop/disconnect must cancel pending approvals; late replies must not authorize a different call. Offer one-call approval and, where the scope can be reliably displayed and matched, approval for the current live session as defined in D-02. Session approval is not Unrestricted execution. A mode change must not silently approve an already pending action.

Third-party extensions can execute code outside ordinary tool calls. Their trust and coverage must be disclosed; do not claim all extension code, shell subprocesses or network activity is constrained by the approval UI. Approval coverage must pass a spike before this requirement can be accepted.

### REQ-007 — Post-edit change review

Expose affected files, relevant text differences and source navigation. Clearly say changes have already been applied; post-edit diff is not pre-edit approval. Distinguish tool-reported targets from workspace changes observed during the task. Show before/after differences where reliable capture is possible; Git-versus-HEAD is a workspace diff, not automatically a task-only diff. Shell activity and concurrent editing may mix other changes into observations: disclose that limitation instead of promising complete task attribution. A Git link alone does not satisfy review. No per-hunk accept/reject, one-click rollback, universal undo or automatic Git reset/stash is included.

Preserve existing user modifications. For identifiable writes the extension can control, block writes to a document with unsaved editor changes and require the user to handle those changes first; never auto-save them to make a write proceed. This revised target was not delivered by WI-010. WI-016 implements the scoped built-in write/edit guard; ACTIVE owns executable evidence and pending acceptance. Shell and trusted-extension bypass paths, and edits after the final pre-execution check, prevent a promise of complete dirty-buffer protection.

Review snapshots are guaranteed only within the current live runtime session, including sidebar hide/recreation. After runtime restart or session switch, disclose that previous diff snapshots may be unavailable; no cross-session snapshot persistence is promised. Retain captured before/after differences as historical operation snapshots if the file changes later, with a changed-file notice when detectable. Source navigation does not guarantee old line positions; never silently substitute current Git differences or overwrite current files from these snapshots.

### REQ-008 — Session continuity

Support new conversations and a list of saved pi sessions in the current project for deliberate selection, including sessions last used in terminal pi, not only this extension's known sessions. Restore dialogue history and project identity, not historical code state or temporary grants. Stop current work and wait for settlement before switching; no hidden task may continue. Reloading the view must not silently duplicate a task. Missing/unavailable sessions and restoration failures need explicit recoverable errors; never silently restore into a different project.

Terminal and extension use sequential handoff: exit the original entry point before restoring the same saved session, and require user confirmation that it has exited. Disclose that confirmation does not enforce exclusive ownership; simultaneous driving, live takeover and an ownership guarantee are not promised. Apply controlled-default and fresh-grant rules on restoration. Use public pi session APIs, not parsing/rewriting session files. Global cross-project history discovery, concurrent sessions and branching UI remain deferred. Listing and safe handoff feasibility require separate integration assessment.

If a historical extension is not currently loaded, display recoverable history and disclose missing capabilities when identifiable; allow continuation with current capabilities. Do not automatically load/install extensions or portray historical tools as currently available. Missing tools must not report fabricated success. Complete dependency detection is not promised; an upstream restoration failure follows the explicit unready/recovery path instead.

Without a dedicated renderer, use bounded, safe generic presentation of available tool identity, status, text and supported structured data. Clearly mark truncation and unsupported content; never execute historical code to recreate a UI. Presentation limits do not define the model's restored context, which remains owned by pi's public session APIs.

For long histories, initially show a recent segment, disclose earlier history and allow progressive loading backwards. Determine batch/rendering budgets through performance validation; bounded or collapsed tool output must disclose omissions. UI history windows do not redefine the model context. Historical attachment text retained by public session APIs must be viewable as a historical snapshot; when information is insufficient, report it as unavailable, never reread today's file as the original attachment. No extra attachment persistence guarantee is included.

### REQ-009 — Representative pi compatibility

**Custom-extension loading goal (confirmed 2026-09-22):** allow the user to explicitly select and load an existing or AI-authored pi extension through supported public pi loading APIs, under REQ-006's controlled default, explicit execution consent and covered-tool approvals. AI authorship does not confer trust or compatibility; the same review, warnings, failure behavior and supported-scope checks apply. AI authoring may happen outside this plugin. A built-in generator/editor, marketplace/install UI and package-management delivery are not implied. How users identify/select loading targets and how those targets are validated remain Prepare decisions, not approved UI or automatic discovery/execution. Later acceptance must exercise consent/decline, loading failure and supported behavior for both origins; no such new acceptance is claimed here.

Local answer invalidation, local transport progress and observed owned-child exit are valid evidence of their respective facts. They must not be presented as remote answer consumption or universal extension completion. Exact remote close timing, per-answer ACKs and globally authenticated operation sources are not universal product requirements. Missing evidence blocks the particular claim or dependent operation, not the entire project pending a new upstream protocol; retain the Stop and recovery rules below.

Ordinary extension-dialog cancellation ends that interaction and returns the protocol's cancellation result, not a default selection or approval. The extension may continue according to its own logic; Stop is separate. A denied covered tool call must not execute. Stop invalidates pending interactions: late answers must neither complete invalidated requests nor authorize replacement requests. This does not guarantee termination of extension code executing outside the covered protocol; unmet lifecycle requirements are compatibility gaps.

**Stop-incompatible interactions (discussion choice, 2026-09-22):** if a known extension command/interaction cannot satisfy the Stop contract, mark that operation unsupported and direct the user to terminal use. Retain independently verified capabilities where they can be reliably distinguished; otherwise exclude the whole extension from the supported compatibility scope. Do not introduce automatic runtime termination/restart as a compatibility workaround. This does not remove existing runtime-failure/shutdown handling or promise automatic detection of every incompatible extension. If the problem is discovered with an interaction already pending, invalidate host-side answers, expose “stop not confirmed / cannot continue,” block new tasks and instruct the user to manually end the runtime before deliberate recovery. Do not claim the upstream extension has stopped or side effects were reversed; this failure-state behavior remains a target requiring verification, not existing product acceptance.

**Standard interaction presentation (WI-013 discussion):** prefer a unified Pi sidebar presentation for select/confirm/input/editor, retaining operation context and Stop/failure visibility. Without an upstream response deadline, do not add a blanket human-response countdown; honor explicit upstream deadlines. Transport failure and Stop settlement deadlines are separate from time spent reading or answering. Present one interaction at a time with a bounded pending queue and visible pending count; queuing must not extend upstream deadlines. On queue overflow, retain accepted requests, cancel/reject additional requests through supported protocol responses and show a warning; cancellation may let extension code continue. Sustained incoming requests enter an explicit interaction-failure state and block new tasks, without automatic restart or claiming execution has stopped. Exact capacity, sustained-overflow thresholds and payload budgets remain unresolved and must be specified before Build; no implicit approval or silent replacement of an older request.

Preserve five capability categories through agreed representative success and failure fixtures, while disclosing unsupported cases:

1. **Provider/model configuration:** reuse existing configuration and demonstrate selection; missing/unavailable configuration or failed switching must not silently substitute another model/provider.
2. **Resources:** demonstrate AGENTS.md, skills and prompt effects and project-resource allow/decline behavior; identify excluded resources without conflating resource consent with execution permission.
3. **Extension commands, custom tools and hooks:** demonstrate synthetic examples and failures; prove the controlled profile prevents third-party extension execution, while trusted loading requires explicit consent and coverage warnings.
4. **Standard extension UI:** support standard dialogs and text display, with cancellation, timeout, Stop and disconnect failure paths. Terminal-specific/custom TUI returns to the terminal with explicit limitations; arbitrary terminal UI parity and automatic detection of every incompatible extension are not promised.
5. **Saved sessions:** demonstrate same-project terminal/extension sequential handoff, restored dialogue, grant reset, missing-session errors and failed switching/recovery under REQ-008 and REQ-006.

Before personal installed-VSIX target acceptance, exercise these fixtures, the core coding loop and restart/failure recovery in Windows local VS Code, and verify at least one real extension in addition to synthetic fixtures. Record Cursor evidence separately. Precise fixture inputs, expected outcomes and the real extension remain to be selected; no fixed user extension has yet been nominated. Public release and broad ecosystem compatibility are not established by these checks. API gaps must be reported as blockers or taken back for scope negotiation, not concealed by successful demos.

## Product decisions and open questions

### Historical baseline — D-01–D-04 (2026-09-19)

The following choices are retained as historical approval context, not rewritten retroactively. For future proposals, the 2026-09-22 target in REQ-003/REQ-006–REQ-009 revises extension-known-only restoration and selection-change handling where they differ. Idle-only execution-profile switching is distinct from the historical tool-approval mode switch; the maintainer deferred skipping tool approval beyond this target. Future skip-approval lifecycle rules require separate scope confirmation. Existing WI approvals and acceptance remain limited to their original slices; no new behavior is authorized by this historical text.

- **D-01 — Initial approval policy (confirmed by the maintainer, 2026-09-19).** Default to Ask before actions; automatically allow covered read-only workspace file operations, ask for edits/writes, shell execution and external-path access. This is a tool policy, not a guarantee that shell cannot escape or use the network. Exact tool coverage and failure behavior need verification.
- **D-02 — Approval scope and lifetime (confirmed by the maintainer, 2026-09-19).** Offer **Allow once** and **Allow this scope for this session**; no persistent allowlist in the first release. Display the scope independently from its lifetime. These are this product's rules informed by reference tools, not a claim of identical behavior across their clients.
  - One-call approval binds to the pending call and its arguments; it cannot authorize another call.
  - Session file grants bind to an explicit operation category and file path within the active workspace/session identity. They permit subsequent matching operations, not only the original diff; no implicit directory-wide or shell authorization. External-path access must separately show the target and read/write category and cannot inherit an in-workspace grant.
  - Session shell grants bind to the working directory, complete command and relevant execution conditions; do not automatically widen them to command prefixes. Matching a command does not prove its referenced scripts or effects are unchanged. If scope cannot be reliably represented and matched, offer Allow once only.
  - A session means the current running agent-session instance in its workspace, not a permanently saved transcript. Hiding/reopening the sidebar preserves grants only while that backend session remains alive. Turn completion or Stop does not itself clear granted session permissions; Stop still cancels pending requests.
  - New/switch session, workspace switch or runtime restart clears grants. Restoring a historical session requires fresh approval; do not restore temporary grants from the transcript. Users can inspect and revoke grants; revocation affects subsequent calls, not completed side effects.
  - Acceptance must verify same-scope reuse, re-prompting on changed scope, expiry on the lifecycle events above and protection against late approval replies. The exact matching implementation remains subject to the approval spike. Unrestricted execution is a separate mode governed by the confirmed D-02 addendum below, not inferred from session grants.
  - **Mode lifecycle addendum (confirmed by the maintainer, 2026-09-19):** newly created or re-established runtime sessions start in Ask before actions. Historical-session restoration, runtime restart, extension-host reload and workspace switch do not automatically restore Unrestricted execution. An optional notice may mention the previous mode, but enabling it requires explicit user selection and a warning about direct file/command execution under the user's environment permissions, not isolation.
  - While the same backend session remains alive, hiding/reopening the sidebar, ordinary turn completion and Stop preserve the current mode. Keep Unrestricted execution visibly indicated and allow switching back at any time.
  - Switching to Unrestricted execution must not automatically approve already pending requests. Switching back to Ask before actions applies to subsequent tool calls; it does not undo side effects or stop an already running operation. Use Stop for cancellation.
  - The first release has no permanent Unrestricted-execution default. Project configuration and conversation history must not silently enable it. Acceptance must test reset and preservation boundaries, pending-request handling and the visible mode/warning.
- **D-03 — Resource trust refusal (confirmed by the maintainer, 2026-09-19).** Allow a clearly labeled session without project-local pi resources when VS Code itself trusts the workspace; otherwise do not start. Keep tool approval independent. Verify resource-loading boundaries at startup and session switch; this product decision does not certify runtime behavior.
- **D-04 — Release boundaries (confirmed by the maintainer, 2026-09-19).** Deliver a local workflow covering explicit context, model selection, streaming execution, approval/stop, post-edit review and known-session restoration within the following boundaries:
  - One local workspace folder, with or without Git. No-folder and multi-root states must be explained rather than silently choosing a project. Remote SSH, Dev Containers and WSL extension-host environments are deferred. This project boundary is not filesystem isolation; external-path tool access remains governed by D-01/D-02.
  - Reuse existing pi credentials and model configuration; defer full login/configuration UI. Explain missing credentials, unavailable models and authentication failures, link to pi configuration instructions, and provide an explicit refresh/reconnect recovery path after external configuration. Do not reimplement credential storage or expose secrets to the webview.
  - One active runtime session per VS Code window, not one saved conversation. Support new conversations and choosing among sessions previously used by this extension in the current project. Before switching, stop active work and wait for a settled state; leave no hidden task running. Restore history under D-02's permission/mode reset rules, not historical code state. Parallel sessions, branching UI and global pi-history discovery are deferred.
  - Post-edit review complements, rather than replaces, pre-action approval. Provide affected-file entry points, relevant text diffs and source navigation; label changes as already applied. No per-hunk accept/reject workflow, universal undo, automatic Git reset/stash or checkpoint rollback is promised.
  - Attach only explicit workspace text files or selections with visible paths/ranges, preview and removal. Do not automatically attach unrelated open files. Images, PDFs, recursive directory attachments and external-path attachments are deferred. Unsaved editor contents may be context but must not be automatically saved; disclose possible differences from runtime disk reads. Track changed selections reliably or require reattachment, never silently reuse stale line ranges. Enforce per-attachment and aggregate limits with actionable rejection, not silent truncation; determine exact values in REQ-003 Prepare before Build.
  - Distinguish tool-confirmed target files from workspace changes observed during a task. Preserve pre-existing user changes; Git-versus-HEAD diffs are workspace diffs, not automatically task-only diffs. Show before/after text differences where reliable capture is possible, and disclose shell/concurrent-edit attribution limits. Complete task-only attribution is not promised, but merely linking to Git does not satisfy review. WI-016 records the Goal-approved bounded capture/attribution contract and required evidence; it does not promise complete task-only attribution.

## Technical evidence and validation gates

- Reimplementing pi's agent loop, provider stack, compaction or session storage.
- Automatic risk approval, sandbox guarantees, universal rollback or pre-edit line-by-line approval in this proposal.
- Full authentication UI, global history search, multiple concurrent sessions, multi-root and remote-environment support as initial release commitments.
- Native plan mode, subagents, MCP marketplace, rich attachments and checkpoint UX until separately scoped and verified.
- Editor-tab chat as the default, or native VS Code Chat Participant as the sole UI; optional surfaces remain deferred.
